# 0028. 「引用した記述」が原文にあるかを、know new と doctor が機械で照合する
- 状態: 採用 / 日付: 2026-10-03

## 状況
調査係（researcher）は「引用なし 0 件」と報告していたが、成果物の引用を出所と突き合わせると、抜け・原文との不一致・出所の取り違えが 12 か所あった（issue #36）。本線の確認は 0008 の「成果物の有無と引用の有無」で、引用が書いてあれば中身がずれていても通る。`doctor` も「引用した記述」節が空かどうかしか見ていなかった。ずれた引用がナレッジに昇格すると、出所付きの事実に見えて後から疑われにくい。調査係が安いモデルほど起きやすい。

## 決定
`quote_misses` が reference の「引用した記述」の各行を、同じ stem の `.orig.md`・`.normalized.md`（旧形式は本文の原文節）と照合する。空白と強調記号（`*`・`` ` ``）を除いた部分一致で、「…」「（中略）」で切った断片ごとに見る。行に「」があればその中だけを見る（後ろの注記を外す）。
- `know new`（昇格の入口）が、現在のタスクの references で合わないものだけを 1 件 1 行で出す。合っていれば何も足さない
- `doctor` が同じ照合を全タスクで行い、問題として数える

AGENTS.md は変えない。

## 理由
- issue の提案は AGENTS.md に照合の規則を足すことだった。規則の文は毎ターン送られ（0027）、照合のために本線が Bash を 1 回余分に呼ぶとターンが増える（ターンごとに会話全体を払い直す）。`know new` の中で走らせれば固定分も追加のターンも 0 で、引用が合っていれば出力も増えない
- 規約に書くだけでは守られるとは限らない（0001）。照合は判断の要らない文字列の比較なので、LLM の報告ではなく数えられる側に置く（0016）
- `doctor` は人が叩くもので、エージェントは自分では走らせない。`doctor` だけに入れると昇格の時点で発火しないので、エージェントが必ず通る `know new` に入れた
- 出力は「ファイル・引用の先頭 40 字」だけにして直し方の説明を付けない。`doctor` の警告が雛形の読み直しを誘ってターンが 7 → 18〜23 に膨らんだ前例がある（PR #8）

## 捨てた案
- AGENTS.md の「安いモデルの調査係」の節に照合の規則を足す（issue の提案）: 上の理由
- `scripts/ws` に照合だけのサブコマンドを足す: 呼ぶ指示を AGENTS.md に書く必要があり、固定分が増える
- タスクの成果物（報告文など）に書いた「引用: 「…」」も照合する: テンプレートに書式の決まりが無く、どのファイルが出所かを機械で決められない。引用の正本は references の「引用した記述」にある
- 出所の番号違いを照合する: 番号の書式が無い。上と同じ

## 影響
原文を言い換えた「引用」は `doctor` の問題として数えられる。原文の Markdown のリンク記法をまたぐ引用（`[文字](URL)` の文字だけを引いたもの）は、前後とつなげると外れる。誤検知が出たら正規化に足す。昇格する前に references を直さなかった場合も `know new` は止めない（作った雛形は残る）。

根拠: issue #36、`tests/test_ws.py` の `test_know_new_and_doctor_flag_quotes_missing_from_original`
