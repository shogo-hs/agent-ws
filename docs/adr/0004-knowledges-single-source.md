# 0004. ナレッジの正本は knowledges/ だけ。他タスクの tasks/ は読ませない
- 状態: 採用（「案件をまたぐ知見の置き場は無い」は 0015 で置き換え） / 日付: 2026-09-05

## 状況
案件は日ごとに状況が変わり、古いタスクの資料には提案時の単価や却下された案が残る。エージェントが「念のため」他のタスクを見に行くと、読む量が増え、古い数字を掴む入口にもなる。
## 決定
案件に残る知見（決定事項・仕様・関係者・手順）の正本は `projects/<案件>/knowledges/` だけ。タスクで得た知見は `scripts/ws know new` で昇格し、`tasks/` の中に書き溜めない。現在のタスク以外の `tasks/` 配下は hook が拒否し、理由文で `knowledges/` を案内する（`tasks/index.md` は通す）。他タスクの成果が要るのに無ければ人に聞く。参照したナレッジは `updated` を併記し、記録より新しくなっていたら `doctor` が警告する。
## 理由
bench の新規タスク（Sonnet・各 5 回）で、agent-ws はナレッジ 3 本と現在のタスクだけを読み、他タスクの資料への立ち入りは 0 回。同じ構造で仕組みを外すと中央値 7 回、導入前は 5 回で、処理した入力は 1.3〜1.6 倍・費用 1.65 倍だった（A/B の p は 0.016・0.008）。古い数字の混入はどの条件でも 0 だったので、この材料で示せたのは読む範囲の差であって誤答の防止ではない。
## 捨てた案
- 参照したナレッジの過去の本文を `references/` に写す: git 管理下なので `git log -- knowledges/<file>` で戻れる。写すと正本が二重になる
- タスクを git ブランチや worktree で分ける: 案件の日々の作業はコード変更とは限らない。フォルダのほうが軽い
## 影響
昇格を怠ると次のタスクから見えない（`index.md` の「現在地」「次の一手」の更新と `know new` が終了前の手順）。ナレッジは案件ごとで、案件をまたぐ知見の置き場は無い。
