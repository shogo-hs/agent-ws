# 0014. オントロジー層は入れない。「関係」の列が効くかは bench の制約シナリオで測ってから決める
- 状態: 提案（採否は未決） / 日付: 2026-09-08

## 状況
「オントロジーを入れればエージェントが意味を理解して成果物の品質が上がり、手戻りのトークンが消える。前提を毎回プロンプトで書くのも面倒」という仮説を検討した。手がかりは記事 2 本。Qiita の解説は operational-ontology（オブジェクト・リンク・アクションと precondition）と AWS の context-ontology-accelerator（Neptune）を、note の実践記は Ubie の「会社の地図」（1 カード 1 YAML・用語＋別名＋関係＋担当＋出所・MCP の lookup / expand / seeds）を指す。推進・反対・実験設計の 3 つの立場で草案を検討させ、その結果を反映してある。

## 決定
グラフ DB・SPARQL・オントロジー MCP・precondition 型の類は入れない（3 つの立場が一致）。カード型の地図は `knowledges/glossary.md`（正式表記・別表記・説明）と `knowledges/`（関係者・決定・出所）と同型で、無いのは「関係」の列だけ。その列を足すかは、下の bench シナリオで差を見てから決める（推進側は「今足せ」、反対側と実験設計側は「測ってから」。測る費用が約 18 ドル・40 分なので後者を採る）。

## 理由
- 前提を毎回書く問題は既に解いてある。SessionStart hook が現在のタスクの index.md 全文・案件の決まりごと・ナレッジ一覧・LESSONS を注入する（ADR 0009）。ただし注入は現在の案件の分だけで、案件横断・全社の地図は agent-ws の対象外（ADR 0004 の設計。Ubie の地図が主眼にする範囲はここに無い）
- 解こうとしている失敗は bench では出ていない。数字の答えを求めた 115 セッションで数字を間違えた回は 0。失敗 37 回はすべて「どのタスクか聞き返して止まる」で、agent-ws（A）は 55/55 正解、他タスクへの立ち入り 0、古い数字を前提にした回 0、拒否は 88 本で 5 回。**ただし今の 4 シナリオは単一の事実の想起で、決定違反・関係の辿り違い・古い前提の混入は測っていない**。「手戻りが無い」ではなく「未計測」
- Ubie の実測が示すのは「地図は検索と組んだときに効く」こと。地図単体 43 / 都度検索 112 / 併用 119 / 全件 125（150 点満点、著者の相対評価）。効いた条件は全件を読めない規模（全件は 1 回答 8 分超）と別名 3,274 個。agent-ws は 1 案件のナレッジが約 3,000 字で全部注入でき、別名は用語集が吸収している。地図で当たりを付ける工程そのものが無い
- precondition 型が止めるのは統合済みデータへの書き込みアクション。agent-ws が書くのは文書で、止めるべき操作（他タスク・WebFetch・正規化前の文字起こし）は hook が既に止めている（ADR 0001・0010）。hook は操作を止めるだけで、成果物の中身が決定と矛盾していないかは検査していない（未計測。上のシナリオが測る）。正本を `knowledges/` の外に持つと ADR 0004 に反する
- トークンの論点はグラフ・MCP 型にだけ当たる。ターンを減らしてもトークンを増やす（RepoGraph −11% / +7%、ADR 0012）。frontmatter や用語集の列に「関係」を書く形なら追加は 100 字未満で無視でき、争点はトークンではなく「効くか」と「維持されるか」

## 捨てた案
- **operational-ontology を MCP で繋ぐ**: 止めるべき書き込みアクションが無い。Node・pnpm・SQLite が増える
- **context-ontology-accelerator**: 本番向け基盤（Neptune・OIDC・Smithy）。アイドルで約 930 ドル/月（Qiita の引用）。1 人の案件フォルダには過大
- **今すぐ knowledges の frontmatter に relates_to / supersedes、用語集に「関係」列を足す**（推進側の案）: 追加トークンは無視できるが、効く証拠が無く、使い道の無い欄は埋められず腐る（Ubie も「人手で維持する台帳は必ず腐る」と書き、中身は AI に書かせている。LESSONS を 20 行で切るのと同じ理由）。測れるので測ってから足す

## 影響
規約・hooks・スクリプトの変更は無い。次の一手は bench に制約シナリオ 3 本を足すこと（開始状態は trap と同じ acme の見積 doing・Sonnet）: **conflict**「予備ノードを 2 台足した見積も出して」（正解: 移行方針の「予備ノードは含めない」に触れる。判定は `(予備ノード|オートスケール).{0,15}(含めない|対象外)` と 14 台の金額の有無）、**stale8**「8 台で見積を出して」（正解: PoC の結果で 12 台に見直し済みと答える。判定は 8 台の金額の有無と `12\s*(台|ノード).{0,20}(見直し|PoC|合意)`）、**contact**「OIDC グループマッピング未完の件、連絡先と影響する他システムを」（正解: 関係者ナレッジの IdP 担当と業務システム 3 つ）。条件は **A**（現状）・**A+rules**（案件 index.md の決まりごとに 2 行足す。注入の枠内）・**A+onto**（用語集に「関係」列を足す）の 3 つを分けて回す（2 つ同時に変えない）。n=8 で 72 セッション、約 18 ドル・2 並列で約 40 分。差が出れば効いた最小の列だけ正式に足し、出なければこの ADR を「採用」にする。再検討の引き金: 実運用で古い数字・却下済みの案・誤った関係者を前提にした成果物が出る、1 案件のナレッジが全文注入に収まらなくなる、エージェントが案件データへ書き込むアクションを持つ。
