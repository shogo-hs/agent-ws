# 0015. 案件をまたぐ自社の事実は repo 直下の knowledges/（共通）に置く
- 状態: 採用 / 日付: 2026-09-09

## 状況
0004 はナレッジの正本を `projects/<案件>/knowledges/` に限り、「案件をまたぐ知見の置き場は無い」と明記した。案件をまたいで注入されるのは LESSONS.md の指摘だけ。0014 の検討で、Ubie の「会社の地図」（用語＋別名＋関係＋担当＋出所のカードの束、3 ヶ月変わらない事実だけ）が効くのは案件横断の範囲だと分かった。自社の組織図・決裁範囲・社内システム・標準手順・共通用語は、案件ごとに写すか、毎回プロンプトで説明するかになっていた。
## 決定
- 置き場は repo 直下の `knowledges/`（`projects/` と並べる）。案件と同じ形（`index.md` / `glossary.md` / `NNN_*.md`）で、架空の案件にはしない
- 載せるのは 3 ヶ月変わらない自社の事実だけ。進捗・数値・案件ごとの決定は案件側。組織図は 1 行 1 人か 1 部署で `→所属`・`→上位`・`→決裁` の関係で書く
- 同じ語・同じ事実が案件側と共通側にあれば案件側が勝つ（顧客の組織図は案件、自社の組織図は共通）。用語集は共通 → 案件の順に読み、同じ誤変換は案件で上書きする
- SessionStart が共通の `index.md` の一覧行を案件のナレッジ一覧と同じ形で差し込む（現在のタスクが無いときも）。本文は必要なときだけ Read
- hook は共通 `knowledges/` の読み書きを現在のタスクの有無に関係なく通す。0010 の拒否（`projects/` 横断・ルートの一覧と検索）は変えない
- 1 ファイル 1 担当（frontmatter の `owner`）。`doctor` は `owner` 空と `updated` 90 日超を警告する
- CLI は `know new --common --owner <担当>` と `glossary add --common`
## 理由
- 注入の増分は見本（組織図 1 枚・用語 3 語）で 274 字（現在のタスクあり 1,836 → 2,110 字、無し 136 → 410 字）。1 ターンの再送（約 39k トークン）に対して無視できる。共通側が無ければ増分は 0
- Ubie の実測が示すのは、地図が効くのは全件を読めない規模で検索と組んだとき。共通側は数枚で全部一覧に載る規模なので、lookup / expand の道具は要らず、一覧の注入と Read で足りる
- 「人手で維持する台帳は必ず腐る」（Ubie）への手当が担当と 90 日の警告。埋まらない・更新されないこと自体が消す根拠になる
## 捨てた案
- 架空の案件 `projects/_common/`: タスク階層と「案件の決まりごと」が付いて回り、hook の案件判定にも混ざる
- LESSONS.md に書く: 指摘の置き場で、事実を入れると 20 行の上限をすぐ超える
- 共通側を優先: 顧客の組織図（案件）が自社の組織図（共通）に上書きされる
- 共通側に lookup / expand の MCP を付ける: 0014 で捨てた重い層に戻る。一覧が注入に収まらなくなったときに再検討
## 影響
0004 の「案件をまたぐ知見の置き場は無い」はこの ADR で置き換え。`projects/` の正本の規則は変えない。`templates/common/` と `templates/knowledge.md` の `owner`、`scripts/ws` の注入・`load_glossary`・`doctor`・`--common`。bench の corpus は変えない。見本の `knowledges/` は 90 日後に `doctor` が警告するので、使う人は自社の事実に置き換える
